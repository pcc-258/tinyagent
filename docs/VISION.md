# TinyAgent — 愿景与架构设计

> v0.1 草案 · 2026-09-21 · 状态：方向探讨
> 本文档定义**模块**（职责、边界、协作），不定义接口签名。接口细节留待模块设计阶段。

---

## 1. 一句话定位

**TinyAgent 是一个进程内嵌的 Go agent 内核。**

接入方在自己的业务代码里 `import` 它，几行代码就能让程序拥有一个完整的 agent —— 会话、工具调用、上下文压缩、审计 —— 无需启动 CLI、无需 sidecar、无需与外部 agent 进程通信。

---

## 2. 为什么需要它

### 2.1 现有 Go agent 生态的断点

| 断点 | 证据（2026-09-21 调研） |
|---|---|
| 想要纯库嵌入，默认却是 CLI | `google/adk-go` 65 行 quickstart 结尾是 `full.NewLauncher().Execute(...)`；47 个示例中 42 个走 CLI launcher |
| 想要轻依赖，却被塞进 gRPC / OTel / gorm / cloud SDK | `adk-go` 的 `go.mod` |
| 想要开箱即用，却要手写工具循环 | `langchaingo` 的 function-call 示例 **149 行全是手写** |
| 想要长期维护，项目已停更 | `langchaingo` 最后 push 2026-01-11，issue #1486 标题即 "is this project dead?" |
| 想要多参数工具，接口只给单参数 | `langchaingo` 的 `Tool.Call(ctx, input string) (string, error)` |

### 2.2 唯一接近的方案及其代价

`cloudwego/eino` 是唯一同时满足「轻依赖 + 纯库 + 内置 ReAct」的项目（`go 1.18`，核心约 6 个直接依赖）。代价是**五套心智模型**（`graph` / `chain` / `dag` / `workflow` / `agent`），ADK 层仍在 alpha，模型实现外置到 `eino-ext`。

### 2.3 TinyAgent 的位置

> 三条硬约束同时成立，且**只有一个心智模型**。

## 3. 核心价值主张

| # | 主张 | 含义 |
|---|---|---|
| 1 | **进程内嵌** | 无 CLI、无 sidecar、无 IPC。就是函数调用。 |
| 2 | **状态透明** | 会话、消息、工具调用记录、压缩结果都是公开可读写的类型。接入方拥有全部状态。 |
| 3 | **默认够用 + 不侵入可换** | 库作者选定一套默认，开箱即用；每个模块都能简单、不侵入地替换 —— **包括 agent loop 本身**。 |
| 4 | **崩溃不带崩主程序** | 接入方代码 panic、库组件 panic，一律捕获且可见。 |
| 5 | **零依赖核心** | 核心只用 stdlib。适配器各自独立 Go module，import 才拉依赖。 |
| 6 | **高易用性** | OpenAI 兼容协议原生支持，合理默认值，开箱即跑。 |

### 3.1 设计原则

#### 原则一：默认够用，且不侵入可换

库提供**一套默认配置与策略**来构建 agent —— 这套默认由库作者选定，开箱即用。接入方默认不需要配置任何东西，也不需要成为 agent 专家或自己调优参数。

> "够用"的基准由库作者把握：**是作者认为最强、最够用的那一套**，而不是随手填的占位值。

但每一个模块都必须提供**简单、不侵入的替换机制**：

- 替换任一模块，**不需要改动其他模块的代码**
- **不需要理解库的内部实现**
- **不需要 fork 或复制粘贴**

**这条原则的两个推论：**

1. **"够用"不等于"能用就行"**。默认的质量决定了不侵入承诺的真假 —— 若默认不好用，接入方就被迫去改，那"不侵入"就退化成"必须侵入"。

2. **"不侵入"的前提是模块边界干净**。模块之间只能通过公开契约交互，任何隐藏耦合都会让"替换"变成"侵入"。这就是 §6 每个模块都要写清「边界（不做）」的原因 —— 边界不是文档装饰，是这条原则的结构性保障。

#### 原则二：替换性有预算，不为纯粹性牺牲可用性

模块替换性做得越彻底，模块间的交互协议就越复杂。极端情况下，这套协议会自己长成一个新系统 —— 这是已被命名的反模式：

> **Inner-Platform Effect（内平台效应）** —— 系统被设计得如此可定制，以至于变成了它所在平台的一个劣质复刻。
> （Alex Papadimoulis 于 2006 年命名）

**因此：**

- **替换性是有限预算的，不是越多越好。** 每增加一个可替换点，都要先问：**真实的替换需求存在吗**？还是只是"将来可能需要"？
- **当"纯粹抽象的协议"与"可用的协议"冲突时，选择可用。**
- **必要时接受扩展字段、escape hatch、甚至"丑陋"的协议设计。** 务实优先于优雅 —— 协议里留一个 `Metadata map[string]any` 或 `Extra json.RawMessage`，胜过为了类型纯洁而让替换变得做不到。
- **本愿景是"我们能做到的最好"，不是"理论上的完美"。**

> 附注：内平台效应并非总是坏事 —— 当它服务于**可移植性**或**权限隔离**时（例如 Java 为了跨平台而构建自己的抽象层）是正当的。关键在于**有意识地取舍**，而非无意识地滑入。

## 4. 能力边界（诚实声明）

边界说不清楚，卖点就是虚假宣传。

### 4.1 保证做到

| 保证 | 机制 |
|---|---|
| 接入方提供的组件 panic，不传播到宿主 | 每个组件调用点包裹 recover |
| **库自身默认组件**的 panic 同样被捕获 | 无豁免。默认组件崩溃 = 库有 bug，必须暴露 |
| panic 一定**可见**，绝不静默吞掉 | 三通道同时输出（error + 事件 + 日志） |
| 不泄漏 goroutine | 库内 goroutine 生命周期绑 context，各自带顶层 recover |
| 不死循环 | 迭代上限 + 超时 + token 预算三重约束 |
| 不因并发写崩 | 会话状态内部加锁；同一会话并发运行被拒绝 |

### 4.2 不保证（进程级致命错误，任何进程内库都拦不住）

`os.Exit()` / `log.Fatal()` · `runtime.Goexit` · 栈溢出 · OOM · **并发 map 写** · cgo 段错误

> `并发 map 写` 是 Go 库最易触发的 `fatal error`，`recover` 完全无效。

### 4.3 panic 可见性机制

**原则：panic 报告内建强制，不做成可插拔 Hook。**

> 反例警告：若 panic 报告做成 Hook，用户不注册 = 静默吞掉 = 直接违反核心主张 4。**因此 Hook 模块中不存在 panic 钩子。**

三通道：① error 返回（携带组件名、panic 值、堆栈）② 事件流中立即推出一条 panic 事件 ③ 结构化日志，默认开启、不可关闭、可重定向。

**措辞纪律**：对外只能说 *"recovers panics raised inside component callbacks"*，**绝不能说 "never crash"**。

### 5.1 第一版（MVP）：验证核心能力与亮点

**目标：一个能快速跑起来、验证核心能力和亮点的版本。**

| # | 要验证的 | 对应主张 |
|---|---|---|
| 1 | 进程内嵌，无 CLI / 无 sidecar | 主张 1 |
| 2 | **崩溃不带崩主程序** | 主张 4（**头号亮点**） |
| 3 | 几行代码接入 | 主张 6 |
| 4 | 状态完全自主 | 主张 2 |
| 5 | 默认够用 + 模块不侵入可换 | 主张 3 |

**范围（全部为第一版标准功能，不可缺省）**：

| | 模块 |
|---|---|
| M1 | Agent Loop |
| M2 | Tool |
| M3 | Store |
| M4 | 上下文管理 |
| M5 | **Audit** —— 标准功能，不可缺少 |
| M6 | Hook |
| M7 | Model |
| 横切 | 数据模型 · 错误与 panic · 装配 |

**第一版刻意不做**：一切"可以做、但会拖慢验证"的东西 —— 见 5.2。

### 5.2 后续版本（TODO）

这些**可以做**，但不进第一版：

- **沙箱隔离**
- **硬资源限制**（CPU / 内存 / 调用次数等）
- **agent 编排** —— 可做，但**不是 DAG 形式**
- 更多 provider 适配
- **MCP 工具来源** —— 复用现成 Go SDK，不自建协议

### 5.3 明确不做

- **DAG / 工作流图编排** —— 不做
- **RAG 框架** —— 不做，不沾边
- **Prompt 模板引擎** —— 不做，不沾边
- **长期记忆模块** —— 不做模块，**但库必须提供 hook 系统 + 上下文管理模块**，让用户能自行搭建记忆系统。库给原语，用户组装
- **发明新协议** —— 不自建 provider 协议，直接适配主流几家（OpenAI 兼容 / Anthropic 等）

### 5.4 由主程序负责

- **多租户隔离** —— 主程序自己做，库不承担这个职责

### 6.4 各模块定义

#### M1 · Agent Loop

**定位**：agent 的心跳。驱动「调用模型 → 执行工具 → 结果回填 → 再调用模型」的迭代，直到产出最终回答或触达上限。

**职责**
- 迭代控制：上限、终止条件、单轮与全局超时
- 调度：何时调模型、何时执行工具、何时压缩上下文
- 并行工具编排：一次返回多个工具调用时并行执行，**结果保序**
- 生命周期：`context` 取消的传播与清理
- 串联：把 M7/M2/M4/M6/M5 按正确顺序串起来

**边界（不做）**
- 不碰模型协议细节 → 委托 M7
- 不碰工具 schema 与执行 → 委托 M2
- 不决定压缩算法 → 委托 M4
- 不碰持久化 → 委托 M3

**对外能力**：流式运行（返回事件流）、同步运行（收集版）

**替换点**：**整个 loop 可替换**。这是「深度可换」主张的核心 —— 接入方若想用自己的循环逻辑，替换这一个模块即可，其余模块照常复用。

**关键约束**
- 事件产出只能在主 goroutine 进行，禁止在工具 goroutine 里直接产出
- 并行工具的结果必须收集后由主 goroutine 顺序产出
- 消费者提前退出时，必须立即取消 `context` 并等待所有工具 goroutine 退出

---

#### M2 · Tool

**定位**：agent 的手脚。把宿主的能力暴露给模型。

**职责**
- 注册：名称、描述、参数 schema
- schema 生成：从 Go 类型反射生成 JSON Schema，或接受手写 schema
- 参数解析与校验
- 执行与单次超时
- 结果规范化：区分「业务软错误」（作为观察喂回模型，循环继续）与「框架级失败」（终止本次运行）
- 工具来源扩展：本地注册 / MCP / 其他

**边界（不做）**
- 不含业务逻辑 → 由接入方实现
- 不做权限审批 → 用 M6 Hook 实现
- 不做调用调度 → 是 M1 的职责

**对外能力**：注册、查找、列举、执行

**替换点**：注册方式（泛型 / 接口）、工具来源（本地 / MCP）

**关键约束**
- **必须支持多参数工具**。单参数是 langchaingo 已被证实的反模式
- 工具执行必须感知 `context`，否则取消无效并泄漏 goroutine
- 工具 panic 必须被捕获并转为可见错误

---

#### M3 · Store

**定位**：会话状态的持久化契约。**只管存取，不管语义。**

**职责**
- 读取会话快照
- 追加消息（批量、原子）
- **重写历史**（压缩必需）
- 列举会话
- 删除会话

**边界（不做）**
- 不解释状态含义 → 那是 M1 / 会话层的事
- 不承担审计 → M5 有独立的存储语义
- 不管理内存态 → 会话的内存表示由 M1 持有

**对外能力**：读 / 追加 / 重写 / 列举 / 删除

**替换点**：内存（默认）· sqlite · mysql · 接入方自定义

**关键约束**
- **必须支持重写历史**。纯 append-only 无法表达压缩（N 条旧消息 → 1 条摘要）。若接口只提供 append，发布后再补是破坏性变更
- 批量写必须**原子**：一次运行产生 user + assistant + tool 多条消息，中途失败不能留半截状态
- 返回的是**纯数据快照**，不是内存对象。否则持久化格式与内存模型绑死，遇到不可序列化字段即炸
- 实现者必须保证并发安全（多会话并发）

---

#### M4 · 上下文管理

**定位**：**负责全部上下文处理**。决定模型每次看到什么、以什么形式看到、以及什么内容被移出上下文。

**职责（策略维度，不是具体算法）**

| 策略 | 做什么 | 典型场景 |
|---|---|---|
| **预算** | token 计算与分配：消息 + 工具 schema + 系统提示 + 每轮固定开销 | 所有场景的前置 |
| **截断** | 丢弃最旧 / 中段内容 | 长对话，近期才重要 |
| **压缩** | 摘要、合并多轮 | 需要保留语义的长历史 |
| **卸载** | 大块内容（如巨型工具结果）移出上下文，只留引用或摘要，需要时再取回 | ES 查询返回超大结果集 |
| **选择** | 按相关性决定注入哪些历史 | 长历史 + 检索式召回 |
| **保护** | 系统提示、最近 N 轮、工具调用配对不可动 | 与上述策略组合使用 |

策略**可组合、可替换**。压缩只是其中一种，不是全部。

**边界（不做）**
- 不做持久化 → 委托 M3（**卸载的落地位置待定**：复用 M3 还是独立的暂存，见 §9）
- 不调用模型 → 委托 M7（摘要式压缩若需调模型，经 M1 协调）
- 不决定「何时」处理 → 由 M1 在每轮调用前触发，M4 提供能力

**对外能力**：预算计算、各类上下文处理策略

**替换点**：**每一种策略独立可替换**，而非只有一个"压缩器"可换

**关键约束**
- **处理后必须保持「工具调用 ↔ 工具结果」配对完整**，否则 OpenAI API 直接返回 400。这是最容易踩的坑
- 上下文处理是有副作用的操作（可能调用 LLM、可能落盘），必须产生可见事件，不能静默发生
- 预算计算必须覆盖工具 schema —— 工具定义本身往往很耗 token，只算消息会严重低估

---

#### M5 · Audit

**定位**：agent 行为的**不可变记录**，供事后追溯、排障与合规。

**职责**
- 记录会话生命周期：创建、运行开始 / 结束、失败
- 记录每次模型调用：请求摘要、响应摘要、token 用量、耗时、重试次数
- 记录每次工具调用：工具名、参数、结果、耗时、状态（成功 / 业务错误 / 被否决 / panic）
- 记录横切事件：panic、上下文压缩发生、Hook 否决
- 提供查询 / 导出能力

**边界（不做）**
- 不拦截、不修改行为 → 那是 M6
- 不作为主流程的同步依赖 → 写入失败不能拖垮运行
- 不与 M3 混用存储 → 语义不同（会话状态 vs 行为流水），存储要求也不同

**与相邻概念的区别**（最容易混淆，必须写清）

| | M5 Audit | M6 Hook | 事件流 |
|---|---|---|---|
| 方向 | 旁路记录 | 同步拦截 | 运行时推送 |
| 能否改变行为 | 否 | **是** | 否 |
| 可靠性要求 | 应尽量不丢 | 不适用 | 可丢（消费者可忽略） |
| 时序 | 事后追溯 | 事前 / 事中介入 | 实时 |
| 典型用途 | 合规、追责、审计查询 | 权限校验、参数改写、限流 | UI 流式渲染、进度 |

**对外能力**：记录、查询、导出

**替换点**：实现（内存 / 文件 / 数据库 / 接入方已有的日志系统）

**关键约束与待决问题**
- 写入失败策略：降级不阻塞主流程，但**必须上报**（不能静默丢弃）
- 同步还是异步：倾向异步 + 缓冲，但需要明确背压策略与缓冲上限
- **审计是第一版标准功能，默认开启**。开销较大，可配置降级或关闭，但**关闭时必须显式声明**，不能悄悄失效
- 是否需要与 OpenTelemetry 等可观测体系对接

---

#### M6 · Hook

**定位**：接入方介入 agent 行为的**同步拦截点**。

**职责**
- 在关键节点介入：模型调用前后、工具调用前后
- 允许修改：请求内容、工具参数
- 允许否决：返回错误以中断该次调用或整个运行

**边界（不做）**
- 不做记录 → 那是 M5
- 不处理 panic → panic 上报是内建强制机制，**Hook 中不存在 panic 钩子**（见 §4.3）

**对外能力**：注册、链式组合

**替换点**：链式组合，多个 Hook 按序执行

**关键约束**
- Hook 自身的 panic 必须被捕获并降级（跳过该 Hook），不能因接入方的增强逻辑导致整个运行崩溃
- Hook 在热路径上同步执行，必须文档化其性能影响

---

#### M7 · Model

**定位**：与 LLM 交互的**唯一边界**。

**职责**
- 请求构造与协议适配
- 响应解析：文本、工具调用、用量、结束原因
- 流式处理：增量产出
- 重试与退避：429 / 5xx
- 能力探测：是否支持流式、是否支持工具调用

**边界（不做）**
- 不含任何 agent 逻辑（循环、工具调度、压缩）
- 不管理会话状态

**对外能力**：生成（非流式）、流式生成

**替换点**：OpenAI 兼容协议（覆盖 DeepSeek / Ollama / vLLM / 大多数国产模型）· Anthropic · 接入方自定义

**关键约束**
- **流式工具调用是分片到达的**，`arguments` 需逐段拼接。适配器必须聚合完整后才交给 M1 —— 这是适配器的核心复杂度，不可低估
- 只支持非流式的 provider 不应被迫实现流式接口（能力探测而非强制实现）
- 实现者必须保证并发安全

### 6.5 一次运行的模块协作时序

```
1. 接入方调用 Agent.Run(sessionID, input)
2. Agent 从 M3 载入会话快照，组装内存态会话
3. M1 进入循环：
   a. M4 处理上下文（预算检查 → 按策略截断 / 压缩 / 卸载）→ 由 M1 协调写回 M3
   b. M6 Hook.BeforeModelCall（可改写请求 / 否决）
   c. M7 调用模型（流式）
   d. 产出事件：文本增量
   e. M6 Hook.AfterModelCall
   f. 若响应含工具调用：
        - M6 Hook.BeforeToolCall（可改写参数 / 否决）
        - M2 并行执行工具（各自超时 + panic 捕获）
        - M6 Hook.AfterToolCall
        - 结果保序回填，回到步骤 a
   g. 若无工具调用 → 循环结束
4. M3 原子持久化本次产生的全部消息
5. M5 全程旁路记录（不阻塞主链路）
```

### 6.6 依赖方向

严格单向：`装配 → M1 → {M7, M2, M4, M6, M3}`

**M5 是特殊的一个**：它旁路订阅所有模块的事件，**不被任何模块依赖**。这个解耦保证了它**不阻塞主流程**，也让替换实现变得容易 —— 但它是**第一版的标准功能，不是可选项**。

## 7. 关键设计约束（易错点）

1. **事件产出不是并发安全的** —— 并行工具的结果必须收集后由主 goroutine 顺序产出。禁止在工具 goroutine 里直接产出。
2. **事件流单次消费** —— 迭代器只能消费一次，必须文档化。
3. **错误不会自动终止迭代** —— 消费方必须显式检查并退出。实现方停止产出 + 消费方显式退出，是**双重约定**。
4. **消费者提前退出时必须清理** —— 取消 `context`、等待所有工具 goroutine 退出。最易遗漏。
5. **压缩必须保持「工具调用 ↔ 工具结果」配对完整** —— 否则 OpenAI API 返回 400。
6. **流式工具调用分片聚合** —— `arguments` 逐段到达，适配器必须聚合。
7. **工具必须感知 `context`** —— 否则取消无效并泄漏 goroutine。

---

## 8. 并发契约

| 对象 | 契约 |
|---|---|
| Agent 门面 | **并发安全**（依赖构造后只读不可变） |
| 会话 | **不并发安全**；内部加锁；同一会话并发运行被拒绝 |
| M3 Store | 实现者必须保证并发安全（多会话并发） |
| M7 Model | 实现者必须保证并发安全 |
| M2 Tool | 实现者必须保证并发安全 |
| M5 Audit | 实现者必须保证并发安全（多会话并发写入） |

**设计取向**：库应该**默认安全**，而不是「纯数据 + 外部加锁」—— 因为宿主一定会忘记加锁。
